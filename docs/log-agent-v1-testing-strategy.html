Incident Log Analysis Agent

v1 testing strategy - per-component test plans, public eval datasets, and tech-stack exploration setup

Design principle carried over from failure-mode analysis: components that can be unit-tested deterministically (adapters, redaction, DB layer, loop mechanics) get conventional tests. Components whose correctness depends on reasoning quality (templating fidelity, agent conclusions, adversarial catch-rate) need curated eval datasets - a green unit-test suite does not prove those work.

2. Unit-testable components (deterministic)

2.1 Adapters

  • detect() confidence scoring against fixture files per registered format (JSON Lines, Elastic export, Loki export, OTLP).
  • parse() correctness: golden-output diffing - parsed LogRecord list compared field-by-field against an expected fixture.
  • Negative cases: malformed input per format should fail predictably, not silently produce partial/garbage records.

2.2 Redaction

  • Entity detection recall/precision against synthetic PII-injected log lines (emails, IPs, credit cards, SSNs, API keys planted at known positions).
  • Hash consistency: same input value → same hash token across multiple lines and multiple fields (raw text and template params).
  • False-positive check: legitimate diagnostic values (error codes, version strings) should not get redacted by an overly broad pattern.

2.3 Scratchpad DB

  • Schema migrations apply cleanly and are idempotent.
  • run_readonly_sql() rejects INSERT/UPDATE/DELETE/DROP/ATTACH - this is a security boundary, test it adversarially.
  • write_note() enforces the mandatory supporting_evidence_json constraint - a note with empty evidence should fail to write.

2.4 Agent loop mechanics

  • Tool-call budget enforcement: mocked LLM responses that keep requesting tools past max_agent_tool_calls must trigger forced convergence, not run indefinitely.
  • Forced-convergence report explicitly states it was budget-limited (see failure-mode §6.4 in the architecture doc) - assert this string/flag is present, don't just check the loop terminates.

2.5 Report generation (citation faithfulness)

Automated, not manual: for every claim in a generated report, re-fetch its cited log_events/template_id rows from the scratchpad and diff the claim text against what those rows actually contain. This is the automated defense against hallucinated citations flagged as a silent failure mode.

3. Components requiring curated eval datasets

3.1 Drain3 / templating fidelity

Needs ground-truth log templates to measure against - this is a solved benchmarking problem in the log-parsing research community, don't build your own from scratch. Metrics to track per dataset: compression ratio (unique templates ÷ total lines), template-level precision/recall against ground truth, and behavior on rare/long-tail templates specifically (these are the ones most likely to carry incident signal and most likely to be mis-clustered).

3.2 Agent loop + adversarial check (end-to-end reasoning quality)

Needs real or realistic incident scenarios with a known root cause, scored on whether the final report identifies it correctly, at what cost (tool calls, tokens), and whether the adversarial pass improves or degrades the outcome versus the pre-adversarial draft.

4. Public datasets to use

4.1 Loghub-2.0 / Loghub-2k

The standard benchmark for log parsing - directly usable for the Drain3 wrapper eval (§3.1).

  • Covers distributed systems (Hadoop, HDFS, OpenStack, Spark, Zookeeper), supercomputers (BGL, HPC, Thunderbird), OSes (Linux, Mac), server/standalone software (Apache, OpenSSH, HealthApp, Proxifier).
  • Loghub-2k: 2,000 annotated logs per system - fast iteration during development.
  • Full Loghub-2.0: scales to millions of lines per system (Thunderbird alone: ~16.6M lines) - use for stress-testing compression ratio and Drain3 performance at real incident volume.
  • Ground-truth log templates are annotated per dataset, giving a real precision/recall number instead of eyeballing output.
  • BGL and Thunderbird additionally carry anomaly labels (originating in anomaly-detection research) - useful beyond template accuracy, for testing whether the agent loop surfaces the actually-anomalous signal rather than just clustering correctly.

Source: github.com/logpai/loghub-2.0 - freely available for research/academic use; redistribution inside your repo's fixtures requires citing the LogPub paper per their terms (verify exact wording before bundling into an OSS repo).

4.2 LogDx-CI

Closer to your actual use case than Loghub: scores full-pipeline downstream diagnosis quality, not just parsing accuracy.

  • 35 real GitHub Actions failure cases, scored by multiple LLM debugger families plus a tool-using agent - the only found benchmark that evaluates the outcome of LLM-based log diagnosis end-to-end rather than the parsing step in isolation.
  • Directly reusable as an eval corpus for the agent loop + adversarial check (§3.2), since it already scores diagnosis correctness, cost per case, and tool-call count - the same axes proposed in the architecture doc's evaluation plan.

5. Known gaps - no public dataset available

Adversarial-check catch rate

No public dataset scores whether a verification pass catches a plausible-but-wrong conclusion. Plan: hand-build a small set (10–15 cases) from Loghub or LogDx-CI incidents; for a subset, deliberately construct a plausible-but-wrong alternative narrative and check whether the adversarial pass catches it versus rubber-stamping.

Elastic / Loki export-format fixtures

No pre-existing dataset in native Elastic/Loki export shape. Plan: generate these locally by running real stacks against Loghub data - see §6 below - rather than hand-authoring export JSON, since export schemas (nested _source fields, Loki label sets) have quirks easy to get subtly wrong by hand.

Bootstrapper (unknown-format) accuracy

No dataset exists by definition - it's for formats not already covered. Plan: synthetically construct a handful of plausible-but-unseen log shapes (custom delimiter styles, unusual timestamp formats) as an internal eval set, refreshed periodically so the bootstrapper isn't just overfit to a fixed set of shapes.

6. Exploring the target tech stacks hands-on

For Elastic and Loki specifically (v1 priority formats), the goal is authentic export shape, not hand-mocked JSON.

6.1 Elastic / OpenSearch

  1. Run the official Docker Compose single-node setup locally.
  2. Feed Loghub-2k sample files in via Filebeat or Logstash.
  3. Pull real _search API exports - this captures the actual nested _source field structure your adapter needs to handle.

6.2 Grafana Loki

  1. Run Grafana's docker-compose stack bundling Loki + Promtail + Grafana.
  2. Point Promtail at the same Loghub sample files for a fair side-by-side comparison with the Elastic path.
  3. Query via LogQL and export results - captures real label-set structure Loki attaches to log streams.

Using the same underlying Loghub source data through both pipelines gives directly comparable adapter test fixtures, and surfaces store-specific quirks (field nesting, label conventions) that would be easy to miss authoring fixtures by hand.
