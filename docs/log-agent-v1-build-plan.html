Mistify v1 Build Plan

A build order for the incident log analysis agent described in the three v1 design documents — what to settle before writing code, what to build in which sequence, and what to cut if the schedule tightens.

Where this stands. The architecture, scaffolding, and testing documents are unusually complete — module boundaries, config shape, DB schema, and tool signatures are all specified well enough to build from directly. This plan does not re-derive them.

What is missing is a build order, and there are eight unresolved details where the three documents contradict each other or specify a component that nothing actually produces. Four of those are in the "silent failure" category the architecture document itself flags as highest priority. They are cheap to fix now and expensive to fix after the pipeline exists, so they come first.

01Settle these before Phase 1

Each item below is a real inconsistency between the shipped documents, not a design preference. The severity chip uses the architecture document's own vocabulary: silent means the pipeline produces plausible output with no indication anything went wrong.

G1 Redaction runs after the bootstrapper has already called the LLM silent
Docs say
Architecture §2.3a: redaction runs "before anything is written to the scratchpad or reaches an LLM". But §2.2a step 2 sends 20–50 raw sample lines to an LLM for schema inference — and that happens before templating, which is before redaction.
Breaks
Every unknown-format ingest leaks unredacted production log lines to the model. The stage ordering makes the guarantee in §2.3a false exactly when it matters most.
Fix
Move redaction to run immediately after adapter parse(), before both the bootstrapper and Drain3. Redaction becomes the first thing that touches a LogRecord, not the third.
G2 The persisted Drain3 snapshot stores unredacted text silent
Docs say
Drain3 is trained on LogRecord.raw and the tree is persisted to .cache/drain3_state.json (§2.3, config drain3.snapshot_path). Redaction happens after.
Breaks
The snapshot is a durable on-disk artifact containing secrets and PII, sitting outside whatever handling the redacted scratchpad gets.
Fix
Same reordering as G1 closes it. Bonus: templating redacted text is better clustering, since [EMAIL:a7f2] is one token shape where raw addresses are unbounded cardinality. Add a Drain3 mask for the [TYPE:hash] form so the hash suffix does not become the new high-cardinality token.
G3 anomaly_score is load-bearing but deferred to "future" silent
Docs say
It is a column in templates, an enum value in query_templates(order_by=…), and step 3 of the adversarial check is "flag any high anomaly_score template excluded from the draft conclusion". But architecture §4 lists anomaly scoring under future improvements — nothing in v1 computes it.
Breaks
The column stays 0.0. The agent can sort by it and get an arbitrary order. The adversarial check's third and most mechanical test silently becomes a no-op — the one check that does not depend on the model's judgement.
Fix
Ship a cheap deterministic score in v1, computed in SQL after load — no model call, no baseline corpus needed: rarity (inverse log frequency) × severity_weight × burstiness (max events in any 1-minute bucket ÷ mean). Add cross-incident novelty later when template trees are reused. It does not need to be sophisticated; it needs to be non-constant.
G4 Read-only SQL enforced by keyword blocklist silent
Docs say
Scaffolding §7: run_readonly_sql() "rejects INSERT/UPDATE/DELETE/DROP/ATTACH". Testing §2.3 correctly calls this a security boundary and says to test it adversarially.
Breaks
A blocklist over SQL text loses to comments, string literals, CTEs, and PRAGMA. Tested adversarially, it will fail — and the failure surface is a model-authored query string.
Fix
Make SQLite enforce it, not a regex. Open a second connection with sqlite3.connect("file:…?mode=ro", uri=True), set PRAGMA query_only=ON, register a set_authorizer() callback that denies everything except SQLITE_SELECT/SQLITE_READ/SQLITE_FUNCTION on the four known tables, and cap runtime with set_progress_handler. Keep the keyword check as a fast pre-filter for better error messages, not as the boundary.
G5 The default credit-card pattern will redact diagnostic values correctness
Docs say
Scaffolding §6: "credit_card": r"\b(?:\d[ -]*?){13,16}\b", on by default in strict mode.
Breaks
That matches any 13–16 digit run: epoch-millisecond timestamps, request IDs, trace IDs, numeric span IDs. This is the architecture document's own "redaction over-reach destroys diagnostic values" failure mode, pre-triggered by the shipped default — and the destroyed values are exactly the correlation keys the agent needs.
Fix
Gate the match behind a Luhn checksum, and require a separator or non-digit boundary. Add the false-positive corpus from testing §2.2 (error codes, version strings, trace IDs, epoch timestamps) as a standing regression fixture before the pattern library grows.
G6 No incidents record — the CLI's own key has no origin missing
Docs say
investigate and report both take --incident-id, and the scratchpad path is incident_{incident_id}.sqlite. But ingest takes only --source and --format, and no table records an incident.
Breaks
There is no defined point where an incident is created, no way to list incidents, and no home for run metadata.
Fix
Add --incident-id to ingest (defaulting to a date-plus-slug derived from the source), and add a run_metadata table — see G7, which needs the same table.
G7 Per-stage health metrics are mandated but have nowhere to live silent
Docs say
Architecture §6, stated as a design principle: "A pipeline health metric per stage is not optional polish." Compression ratio, bootstrapper match rate, redaction counts, and the budget-limited flag are all named as required signals.
Breaks
The four-table schema has no column for any of them. Without persistence there is nothing for the report to declare, nothing to assert in a test, and no way to notice a run degraded — which is the precise failure the principle exists to prevent.
Fix
Add a fifth table in 0001_init.sql: run_metadata(stage, metric, value, ts). Every stage writes its numbers; the report template reads them into a health block; tests assert on rows rather than on log output.
G8 Citation faithfulness is classified as a unit test correctness
Docs say
Testing §2.5 and the matrix mark report faithfulness as unit — "re-fetch its cited rows and diff the claim text against what those rows actually contain."
Breaks
Checking whether a natural-language claim is entailed by a set of log rows is not a text diff. Written as a string comparison it will pass everything, which is worse than not having the check — it is a green test asserting nothing.
Fix
Split it in two. The deterministic half is a real unit test: every cited log_event.id and template_id exists, falls inside the claimed window, and matches the claimed source and severity. The semantic half is an entailment judge (a third model call, different model from both the loop and the adversarial pass) scored on a labelled fixture set — reclassify it as eval in the matrix.

02Model and API corrections

config.yaml pins claude-sonnet-4-6 for both the loop and the adversarial pass. That model still exists, but it is no longer the right default, and setting both keys to the same value contradicts architecture §6.3, which requires a different model for the adversarial pass to avoid correlated blind spots.

RoleUseWhy
Investigation loop claude-opus-5 Strongest model for long-horizon agentic tool use; 1M context. Run at effort: "high", adaptive thinking on.
Adversarial pass claude-sonnet-5 Satisfies §6.3's different-model requirement. Move to claude-fable-5 if Phase 5 measures the catch rate as the binding constraint.
Bootstrapper schema inference claude-haiku-4-5 Narrow structured-output task over 20–50 lines, gated by a match-rate check that catches a bad answer. No need to spend a frontier model here.
Entailment judge (G8) claude-opus-5 Distinct from the adversarial model so a shared bias cannot rubber-stamp its own citations.

One cache_control breakpoint after it is the single biggest cost lever in the design. One more: Phase 5's eval sweeps re-run the same corpus repeatedly and are not latency-sensitive. Run them through the Batch API at 50% cost.

03Build sequence

The ordering principle: get one thin slice running end to end before widening any layer. The scaffolding document lists components by architectural grouping, which is the right way to organize a repository and the wrong order to build one — it puts four adapters and a bootstrapper ahead of the first line of agent code, and the agent loop is where the design risk actually lives. Phase 1 therefore builds the narrowest possible path from a JSONL file to a rendered report, then every later phase widens one layer of something that already works.

  • anomaly_score computation per G3, as a post-load SQL pass.

3
The real agent loop2–3 days
  • Four tools as @beta_tool functions; Tool Runner drives the loop; every call writes a query_log row.
  • Task budget plus the hard call cap; forced convergence path; the budget-limited flag written to run_metadata and surfaced verbatim in the report.
  • Prompt caching around the system prompt and template digest.
  • Adversarial pass as structured output — a critique that objects, never one that rewrites (§6.2), with objections weighted by evidence strength.
  • The rebuttal step from §6.2: the original reasoning answers the objection with one targeted query before anything finalizes. Cheap, and it is what turns a one-shot veto into a debate.
  • Deterministic half of the citation check (G8) wired into report generation.
  • Mocked-LLM tests: budget exhaustion, forced convergence, the budget-limited string actually appearing in output.
ExitA live run on the Phase 1 fixture identifies the planted cause with citations that resolve to real rows. Cost and tool-call count recorded — this is the first number worth comparing against a baseline.
4
Format coverage and bootstrapper2–3 days
  • Elastic, Loki, and OTLP adapters; registry.detect_format() with the 0.6 confidence floor.
  • Fixtures generated the way testing §6 prescribes — Loghub-2k pushed through real Elastic and Loki Docker stacks, then exported. Hand-authored export JSON gets the nesting and label conventions subtly wrong, and those quirks are the whole point of the adapters.
  • Structural shape clustering; LLM inference as structured output; the match-rate gate; sub-template retry; persisted inferred adapters.
  • Detection confusion matrix across all fixtures, including deliberate near-misses.
ExitEvery fixture routes to the right adapter. sample_unknown_format.log bootstraps above the 0.85 match rate; a deliberately pathological file falls back to raw-line mode loudly, with the reason in run_metadata.
5
Evaluation harness2–4 days
  • Loghub-2k: template precision and recall against annotated ground truth, plus long-tail template behaviour specifically — rare templates are where incident signal lives and where clustering fails.
  • Loghub-2.0 at volume (Thunderbird, BGL): compression ratio and Drain3 throughput at real incident scale.
  • LogDx-CI: end-to-end diagnosis correctness, cost per case, tool calls per case.
  • Baselines on the same cases — grep, tail, and raw injection — because a root-cause accuracy number means nothing without them.
  • The hand-built adversarial set testing §5 calls for: 10–15 cases, a subset carrying a deliberately plausible-but-wrong narrative, scored on catch rate and on false-flip rate against correct conclusions.
  • Batch API for the sweeps.
ExitA scorecard table fit to paste into the README. This is the phase that separates the project from a demo, and it is the one most likely to get squeezed — protect it ahead of Phase 6.
6
MCP server and packaging1–2 days
  • ingest_logs, investigate, get_report over the MCP SDK, sharing the CLI's code path so redaction cannot be bypassed by entry point.
  • A test asserting exactly that: an MCP ingest of PII-laden input produces a scratchpad with no unredacted values.
  • HTML and PDF report renderers; README with the Phase 5 scorecard; install instructions for Claude Desktop and Claude Code.
ExitInstalled as an MCP server in a real client, it ingests and investigates a file end to end without touching the CLI.

Total: roughly 11–17 focused days — call it three to four calendar weeks part-time. Phases 0–3 are strictly sequential; Phase 4 can run in parallel with Phase 5 if Loghub work starts while adapters are being written.

04If the schedule tightens

A descope ladder, from most to least defensible. Each rung is still a coherent thing to show.

Full v1Phases 0–6. Everything in the three documents, evaluated.
Credible v1Phases 0–5, dropping the MCP server. A CLI with a real scorecard beats an MCP server without one.
Minimum defensiblePhases 0–3 plus the Loghub-2k template eval and the grep baseline, JSON Lines only. Narrow, but every claim in it is measured.
Do not shipPhases 0–4 with no evaluation. Wide format coverage and an unmeasured agent is the exact demo the architecture document's §5 warns against.

05Open decisions

Four things I need from you. Each has a recommendation, and each changes what gets built rather than only how it is named.

Package name — mistify or log-agent?

RecThe repo is mistify; the scaffolding document says log-agent/ throughout. Go with mistify for the distribution, package, and CLI, since it is the name that already exists and the docs are the newer thing to amend.

Do the chunking config keys stay?

Recchunk_window_minutes and chunk_overlap_minutes are in config.yaml, but no pipeline stage consumes them — the agent slices on demand via get_slice instead. Drop both for v1 rather than shipping config that does nothing; the overlapping-window idea is already recorded as a future improvement in architecture §4.

Is this portfolio work or something you intend to run on real logs?

RecIt changes Phase 2 and Phase 6 materially. Real logs mean redaction defaults get audited per deployment and the permissive/off modes need guard rails. Portfolio means Phase 5 is the most valuable phase and deserves the extra days. Answer determines where to spend the squeeze.

Start now, or amend the design docs first?

RecAmend first — it is under an hour of edits to fold G1–G8 back into the three documents, and they are the spec everything else is built against. Then Phase 0.
