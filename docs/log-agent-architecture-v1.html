Incident Log Analysis Agent

v1 architecture — a log-compression + agentic-loop framework for LLM-driven incident diagnosis

Goal: Take gigabyte-scale, heterogeneous incident logs, compress them into a queryable representation an LLM can reason over efficiently, let an agent iteratively investigate via SQL slices, adversarially check its own conclusion, then produce a structured incident report — without blowing the context window or losing low-salience but critical signal.

2. Component specifications

2.1 Ingestion adapters

Each adapter's only job is to emit records in a common normalized schema. Format-specific parsing logic is isolated here so the rest of the pipeline never needs to know the source format. Priority shifted toward Elastic/Loki stacks for v1 to match target audience over general infra/network syslog sources.

Any log not matching a known adapter falls through to the unknown-format bootstrapper (§2.2a) rather than failing ingestion.

2.2 Normalized record schema

{
  "ts": "2026-08-30T14:22:01.442Z",   // ISO-8601, UTC normalized
  "source": "checkout-service",       // service/host identifier
  "severity": "ERROR",                // normalized enum: TRACE|DEBUG|INFO|WARN|ERROR|FATAL
  "raw": "original log line, unmodified",
  "fields": { "trace_id": "...", "k": "v" }, // any structured fields extracted
  "format": "json_lines"              // originating adapter, for traceability
}

2.2a Unknown-format bootstrapper

First-class pipeline stage (not a future improvement) — triggers whenever incoming lines don't confidently match any registered adapter.

  1. Structural clustering pass. Group the first sample of lines (~100, more for noisy formats) by shape: token count, delimiter style (JSON braces, pipes, commas, spaces), presence of timestamp-like tokens (regex for ISO-8601 / epoch / syslog-style), presence of severity words. Cheap, no LLM call.
  2. LLM-assisted schema inference (fallback). If structural clustering can't confidently locate timestamp / severity / message fields, send a deduplicated, diverse sub-sample (20–50 lines, not the raw sequential 100) to an LLM with a structured-output prompt to infer a parsing template: field boundaries, which field is the timestamp, which is severity, which is free-text message.
  3. Feed into Drain3. The inferred message-boundary becomes a custom mask/pattern for Drain3 — Drain3 still does the clustering and variable-token extraction once the message boundary is roughly correct.
  4. Validate before committing. Run the inferred template against the next 500–1000 lines; if match rate falls below a threshold (e.g. 85%), assume multiple sub-shapes exist (multiline stack traces mixed with kv-pairs is a common case) and attempt to detect 2–3 sub-templates rather than forcing one.
  5. Persist as a new adapter. Once confirmed, save the inferred regex + field mapping as a lightweight adapter definition so future files from the same source skip LLM inference entirely — mirrors Drain3's own persisted snapshot state, one layer up.

2.3 Drain3 templating layer

Every normalized record's raw field is passed through Drain3 to mine a log template (e.g. "Connection to <*> failed after <*> retries"). This collapses near-duplicate lines into template clusters before anything reaches the LLM.

  • Each unique template gets a stable template_id and a running occurrence count.
  • Parameters extracted per occurrence (the <*> values) are retained separately so the agent can still drill into specifics.
  • Persist the trained Drain3 tree per-incident so templates stay stable if the pipeline is re-run.

2.3a Secret / PII redaction

Runs immediately after templating, before anything is written to the scratchpad or reaches an LLM — inspired by log-essence's approach of stripping sensitive data before any external model sees it.

  • Pattern-based redaction for common entities: emails, IPs, credit cards, SSNs, phone numbers, API keys/tokens.
  • Same-entity → same-hash replacement (e.g. user@acme.com → [EMAIL:a7f2]) so correlation across log lines is preserved without exposing the original value.
  • Redaction applied to both the raw field and extracted template parameters — templates themselves should never leak a real value through a wildcard capture.
  • Configurable mode (strict / permissive) so local-only analysis can optionally skip redaction when nothing leaves the machine.

2.4 SQLite scratchpad — schema

This is the working memory of the whole system: the agent reads and writes here rather than re-reading raw logs on every step.

-- raw normalized + templated records
CREATE TABLE log_events (
  id INTEGER PRIMARY KEY,
  ts TEXT, source TEXT, severity TEXT,
  template_id INTEGER, raw TEXT, fields_json TEXT
);

-- one row per unique template, with stats
CREATE TABLE templates (
  template_id INTEGER PRIMARY KEY,
  pattern TEXT, occurrence_count INTEGER,
  first_seen TEXT, last_seen TEXT,
  severity_mix_json TEXT
);

-- agent's running notes / hypotheses, timestamped
CREATE TABLE scratchpad_notes (
  id INTEGER PRIMARY KEY,
  step INTEGER, note TEXT,
  supporting_evidence_json TEXT,  -- references to log_events / template_ids
  confidence TEXT
);

-- record of every slice/query the agent requested
CREATE TABLE query_log (
  id INTEGER PRIMARY KEY,
  step INTEGER, sql_query TEXT, row_count INTEGER
);

Keeping supporting_evidence_json mandatory on every note is what lets the adversarial check verify claims against hard data instead of re-trusting the narrative.

2.5 Agent loop

Tools exposed to the agent
  • query_templates() — ranked by count / severity / recency
  • run_sql(query) — read-only, scoped to scratchpad tables
  • get_slice(time_range, source, severity) — bounded raw-line pull
  • write_note(text, evidence, confidence) — persist a hypothesis
Loop controls
  • Hard cap on tool calls per incident (prevents thrashing)
  • Forced convergence step if budget is hit without resolution
  • Every step's tool call + result logged to query_log for auditability

2.6 Adversarial check

A separate call, not just "are you sure?" — it is given a distinct mandate and direct scratchpad access rather than only the draft summary:

  1. Verify each claim in the draft against its cited supporting_evidence_json — flag unsupported claims.
  2. Actively search the scratchpad for an alternative explanation not considered in the current line of reasoning.
  3. Check whether any high-severity template with low narrative weight was dropped from the conclusion.

2.7 Report generation

Final call consumes only the verified scratchpad state (notes + evidence, post-adversarial-check) — never raw logs directly — to produce a structured incident report: summary, timeline, root cause hypothesis with confidence, supporting evidence, and open questions.

2.8 MCP server exposure

Package the pipeline as an MCP server (alongside a CLI) so it can be invoked directly from Claude Desktop, Claude Code, Cursor, and other MCP-compatible clients — avoids requiring a standalone UI for v1 and lets the agent loop run inside a client the user already has open.

  • Exposed tools: ingest_logs(path/source), investigate(incident_id), get_report(incident_id).
  • Redaction (§2.3a) runs regardless of invocation path — MCP exposure doesn't bypass it.

4. Known v1 limitations & where the pipeline can improve

Chunk / window boundary loss

A root-cause signal can split across two time windows and lose significance in both. Future: overlapping windows, or a first-pass whole-stream anomaly scan across templates before any chunked deep dive.

Narrative bias toward "interesting" errors

LLMs can deprioritize a correct but mundane signal in favor of a more novel-sounding but wrong one. Future: weight templates by statistical anomaly score (frequency deviation from baseline) independent of the LLM's narrative judgment, and surface that score directly to the adversarial check.

Format coverage

v1 covers JSON Lines, Elastic/OpenSearch, Loki, and OTLP, with syslog/CLF pushed to v1.1. Future: EVTX, structured cloud-provider log formats (CloudTrail, GCP Audit Logs), and direct API adapters for Datadog/Splunk rather than export-file based ingestion.

Static template clustering

Drain3 trees are trained per-incident. Future: persist and reuse template trees across incidents for the same service to detect "first time this error has ever occurred" as its own signal.

No cross-signal correlation beyond logs

v1 reasons over logs only. Future: pull in trace_id-linked spans (OTel traces) and metrics deltas around the incident window so the agent can correlate log anomalies with latency/error-rate spikes.

Single adversarial pass

Currently one adversarial call at the end. Future: lightweight adversarial checks interleaved during the agent loop, not just before the final report, to catch bad hypotheses earlier and cheaper.

No feedback loop from real incident resolutions

Future: once a human confirms/corrects the generated report, feed that back to improve template severity weighting and future adversarial-check prompts (lightweight fine-tuning or few-shot example bank).

5. Evaluation plan

Before claiming this works, benchmark against naive baselines (grep, tail, raw injection) on a small set of real or replayed incidents, scoring root-cause accuracy, cost per case, and tool-call count — the same axes used in recent log-reduction benchmarking work. This is the difference between a demo and something credible.

6. Known failure modes & mitigations

Design principle: every stage must be able to fail loudly with a measurable signal, rather than silently degrading and producing a confident-looking but wrong output. A pipeline health metric per stage is not optional polish — it's what separates this from a demo that only works on clean examples.

6.1 Drain3 ineffective on a given log file

Two distinct failure directions:

  • Under-clustering — high line-to-line variability (stack traces, verbose free-text, high-cardinality unmasked tokens) means almost every line becomes its own template. No compression is achieved.
  • Over-clustering — too-loose similarity threshold/depth merges genuinely distinct error conditions into one template, destroying the signal being compressed for.
DetectionMitigation
Track compression ratio (unique templates ÷ total lines) as a per-run health metric. Ratio near 1.0 = no compression; suspiciously low ratio with wide severity mix inside a single template = over-merged. Calibration pass: try 2–3 sim_th values against a sample, pick whichever lands in a sane compression band. For pathological files (mostly free-text, no repeated structure), fall back to semantic/embedding clustering as a secondary pass. If both fail, degrade to raw time-sliced investigation rather than emitting garbage templates silently.

6.2 Adversarial step overturns a correct conclusion

Real risk if the adversarial call has unilateral authority to replace the draft conclusion.

  • Don't let it rewrite — let it object. The adversarial call produces a structured critique (specific evidence gaps or a specific alternative explanation with its own citations), never a direct replacement of the conclusion.
  • Require evidence-backed objections only. An objection citing no scratchpad evidence cannot flip a well-evidenced conclusion — weight objections by evidence strength, not existence.
  • Add a rebuttal step. The original reasoning gets a chance to respond to the objection with a targeted scratchpad query before anything is finalized — turns a one-shot veto into a real debate, cheaply.

6.3 Adversarial step misses a wrong-but-plausible line of reasoning

The harder failure — a false negative that looks like verification happened.

  • Correlated blind spots are the core risk. If the same model/prompt style produced both the reasoning and the "check," they can share the same bias. Use a different model, or at minimum a different temperature/framing, for the adversarial pass.
  • Force a checklist, not vibes. Not "does this seem right?" — instead: does every claim map to cited evidence? Is there a high anomaly_score template excluded from the conclusion? What's the strongest alternative explanation using only the scratchpad?
  • Needs an eval set to actually measure. A handful of incidents with known ground truth, deliberately including plausible-but-wrong red herrings, so the adversarial pass's catch rate is measured rather than trusted by design.
