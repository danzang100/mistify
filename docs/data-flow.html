Mistify Data Flow

How one line in a log file becomes a line in an incident report — what it is at each hop, and which guarantees hold where.

The ingest spine

One pass, left to right in time. The labels on the arrows are the data's actual shape at that point, not a description of it.

The ordering that everything else rests on

Redaction runs immediately after parse() — before templating, before the Drain3 snapshot is written to disk, and before any line could reach a model. Put it anywhere later and the guarantee fails on the unknown-format path, where the bootstrapper sends sample lines to a model before templating has happened at all.

What each stage does

Adapter format in, records out

Samples the first lines, scores each registered adapter, and takes the best above 0.6. Below that it returns nothing, which is the handoff to the Phase 4 bootstrapper rather than a failure. Malformed lines are skipped and counted, never half-parsed.

Redactor values out, correlation kept

Replaces each detected value with a stable [TYPE:hash]. The same value always yields the same placeholder within an incident, so "this address appears in these fourteen lines" survives redaction even though the address does not.

Calibration side pass

Measures candidate thresholds against a redacted sample and keeps the one leaving fewest templates without merging distinct conditions. It never touches the record stream — its only output is a number the templater is then built with.

Templater many lines, one shape

Mines a shape per message and keeps its own registry of every template ever seen, so Drain3 evicting a cluster from its matching tree can never leave an event pointing at a template row that was not written.

Load bounded memory

Events flush every 5,000 records instead of buffering the file. Templates are written after the events, which is why an explicit orphan check replaces foreign-key enforcement.

Scoring search order

Ranks templates by severity, burstiness and rarity — no model involved. The ranking is the search order, so the rarest and most severe are met before the noise.

What the scratchpad holds

One SQLite file per incident. It is the working memory of the whole system: every stage writes here, and every reader reads here rather than going back to the log file.

incidentsWhich source, when, which format, which redaction mode.
log_eventsOne row per parsed line, redacted, pointing at its template.

scratchpad_notesWhat the investigator concluded. Evidence is mandatory, enforced in SQL.

Three ways out

Why the vault is not a table

The read-only channel can read any table in the database it is pointed at. A vault table living in the scratchpad would be one SELECT away from undoing redaction entirely.

Health metrics, briefly

Every stage publishes a few numbers about its own run into run_metadata, so a degraded run is visible rather than inferred from a report that reads fine. They are declared once in a single vocabulary that writers and readers share, and a handful of them drive warnings in the report — coverage below 1.0, templates evicted, one template dominating the file, the most severe template failing to rank near the top. The rest are shown and not acted on.

The distinction matters for one reason: renaming a metric a reader acts on changes behaviour, and renaming one that is only displayed does not.

What must stay true

Redaction is first

Nothing downstream — templater, snapshot, database, model — ever sees an unredacted record.

Coverage is 1.0

Every event reaches a template. An event whose template is missing is a line no search can surface.

Evidence is mandatory

A note without supporting evidence cannot be written; the constraint is in SQL, not just Python.

Timestamps sort as text

Fixed width, always UTC — string order and chronological order are the same thing.

Ingest is one pass; investigate and report are separate commands over the same scratchpad. The investigation step is still a hardcoded heuristic — the model-driven loop arrives in Phase 3.
